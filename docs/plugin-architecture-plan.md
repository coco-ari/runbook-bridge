# 插件扩展与维护性优化方案

## 目标与边界

未来插件有各自的协议、配置、操作和工作区。公共框架只统一项目与环境作用域、配置版本、连接生命周期、凭据保管、审批和审计；插件以显式注册的代码贡献配置规则、连接适配器、操作处理器和界面，不要求定制功能服从通用 CRUD 模型。

本轮保留 Electron、Broker、MCP 和 React 的现有进程边界，保留现有数据格式、IPC/MCP 名称和产品兼容性标识。不引入运行时下载或执行第三方插件的机制。注册表由可信源码组装，未知类型与未知操作默认拒绝；插件注册不等于获得 Agent 权限。

## 实施顺序

1. **插件配置与运行时扩展点**：提取不依赖文件系统的配置模型；将三个插件的规范化、字段范围和操作分发移入各自贡献模块，建立显式注册表。存储层保留并发、版本、原子写入与恢复。业务调用正式模型 API，停止依赖 `workspaceInternals` 的配置函数。
2. **插件保存应用服务**：将 IPC 中的配置准备、凭据事务、上下文失效、审计和编辑会话保存提取为独立服务。IPC 保留 Renderer 身份和消息转发。保留单一环境变更队列、配置版本校验、凭据重新绑定和保存后连接失败语义。
3. **前端插件贡献与壳状态**：建立可提供定制组件的前端插件入口；收敛插件类型信息与入口选择。将 AppShell 中布局、会话或离开保护等独立职责提取，避免新增插件继续堆积在壳中。现有插件的编辑和工作区体验保持一致。
4. **契约与结构约束**：为插件生命周期的高频 IPC 建立共享通道定义与精确的请求/响应类型；增加契约检查，降低 preload、类型声明和处理器漂移。将被重构职责的源码形状断言替换为行为断言，保留安全和兼容性墓碑测试。
5. **扩展验收与文档**：用仅存在于测试中的第四种插件验证定制配置、操作分发及未知操作拒绝，提供新增插件步骤、责任边界与安全检查位置。同步架构文档并完成相关回归。

## 验收标准

- 内置三个插件均通过注册贡献进入提取后的配置和操作路径，公共存储/调度代码不再为它们维护规范化或调用分支。
- 第四种测试插件能保留自身配置与专属操作，并且不能通过未知能力绕过权限检查；重复或无效注册被拒绝。
- 插件配置保存的版本冲突、凭据事务失败、重新绑定要求、保存成功但重连失败有行为测试；IPC 不拥有这些事务实现。
- 前端贡献允许定制组件，抽出的壳状态有可执行的行为或 UI 回归保护；未保存修改和作用域切换行为不退化。
- 高频插件 IPC 的通道和返回类型有一致性检查；不把敏感字段放入公共快照。
- 运行相关测试、`corepack pnpm run check`、`corepack pnpm test`、`corepack pnpm run test:ui` 及受影响的插件 UI 测试。涉及 MCP/打包边界时运行构建、包验证和打包 MCP/UI 冒烟。
- 不提交生成目录、凭据或本地应用数据。安全门、主机指纹核验、上下文和一次审批精确绑定保持原行为。

- 已建立插件生命周期 IPC 目录及真实 preload 契约检查，补充编辑保存结果类型。

- Agent 安全门保持独立显式规则；新增插件注册不会授予权限。凭据绑定、新协议验证及路由仍需专门设计，详见插件开发指南。
